Plan de trazabilidad operativa

DANA-API-WRITING · Revisión del 18 de agosto de 2026

Este documento organiza los mensajes operativos y las auditorías administrativas que conviene completar antes de producción. Los logs de PM2 sirven para diagnóstico; las acciones que requieren evidencia permanente deben conservarse en MongoDB.

Regla general: registrar una acción solamente después de que la operación haya sido confirmada. No imprimir contraseñas, hashes, tokens, cookies, secretos, rutas locales completas ni contenido de archivos.

1. Estado actual

2. Paso 1 — Creación manual de archivos

Reemplazar el mensaje técnico de inserción por un único mensaje posterior al guardado:

[Create] Completed. {
  fileName: 'Nombre del archivo',
  type: 'RM',
  site: 'gaiim',
  creationDate: 'fecha ISO',
  user: 'usuario'
}

Eliminar del log exitoso los nombres internos de base de datos, colección y el ID de MongoDB.

3. Paso 2 — Administración de usuarios

Actualizar acceso

[UserAccess] Completed. {
  targetUser: 'usuario modificado',
  isActive: true,
  role: 'user',
  site: 'gaiim',
  updateDate: 'fecha ISO',
  performedBy: 'administrador'
}

Eliminar usuario

[UserDelete] Completed. {
  targetUser: 'usuario eliminado',
  deleteDate: 'fecha ISO',
  performedBy: 'administrador'
}

Como mejora posterior, crear una auditoría MongoDB con before/after para cambios de acceso. Los trabajos históricos del usuario deben conservarse.

4. Paso 3 — Seguridad de la cuenta

[Password] Updated. {
  user: 'usuario',
  updateDate: 'fecha ISO'
}
[GoogleAccount] Unlinked. {
  user: 'usuario',
  unlinkDate: 'fecha ISO'
}

No registrar contraseñas anteriores o nuevas, hashes, tokens JWT, cookies ni identificadores de sesión.

5. Paso 4 — Operaciones directas de Master Files

Importar

[MasterFileImport] Completed. {
  fileName: 'Master RM', type: 'RM', sites: ['gaiim'],
  recordCount: 1200, importDate: 'fecha ISO', user: 'administrador'
}

Editar

[MasterFileUpdate] Completed. {
  fileName: 'Master RM', type: 'RM',
  inserted: 2, updated: 10, deleted: 1,
  updateDate: 'fecha ISO', user: 'administrador'
}

Copiar

[MasterFileCopy] Completed. {
  sourceFileName: 'Master original', copiedFileName: 'Master copia',
  type: 'RM', copyDate: 'fecha ISO', user: 'administrador'
}

Eliminar

[MasterFileDelete] Completed. {
  fileName: 'Master eliminado', type: 'RM', deletedRecords: 1200,
  deleteDate: 'fecha ISO', user: 'administrador'
}

Crear posteriormente una auditoría MongoDB para importaciones, ediciones, copias y eliminaciones directas. La auditoría de sincronización actual no sustituye esta evidencia.

6. Paso 5 — Acciones opcionales

  • Exportación de catálogos: registrar usuario y fecha si se desea conocer quién extrajo la información.
  • Reintento de Master Sync: registrar archivo, tipo, sede, usuario y resumen added/updated/unchanged.
  • Registro público: registrar correo o nombre y fecha, nunca contraseña o token.

7. Acciones que no necesitan log de éxito

  • Listados y consultas de archivos, usuarios o catálogos.
  • Abrir editores, consultar auditorías o buscar Part Number.
  • Validar filas y cargar opciones de catálogos.
  • Importar Excel únicamente para mostrarlo en el editor sin guardar.
  • Lecturas normales de perfil y descargas rutinarias.

8. IDs internos y seguridad

Los ObjectId de MongoDB no son credenciales. Se pueden omitir de los logs exitosos para mejorar legibilidad. En errores técnicos pueden conservarse porque permiten correlacionar el incidente con el documento correcto.

Los logs del backend aparecen en la terminal de desarrollo y en los archivos administrados por PM2; no se envían automáticamente a la consola del navegador.

9. Orden de implementación y verificación

  1. Corregir el mensaje de creación manual.
  2. Agregar logs de administración de usuarios.
  3. Agregar eventos de seguridad de cuenta.
  4. Agregar logs de acciones directas sobre Master Files.
  5. Crear auditoría MongoDB para usuarios.
  6. Crear auditoría MongoDB para Master Files directos.
  7. Evaluar eventos opcionales.
  8. Ejecutar npm test, npm run build y git diff --check.
  9. Probar cada acción con éxito y error, confirmando que no aparezca un mensaje Completed falso.
